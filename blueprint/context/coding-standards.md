# Coding Standards

> Generated by `/adopt` from the real project (Next.js 16 App Router marketing
> site, no database, no auth). Edit as conventions evolve; re-run `/adopt`
> never overwrites this without confirmation.

## TypeScript

- Strict mode enabled (`tsconfig.json`).
- Define `interface`s for props and data shapes (see `Testimonial` in
  `src/app/about/page.tsx`).
- Use type inference where obvious, explicit types where helpful.

## React

- Functional components only.
- Server components by default; `"use client"` only where interactivity is
  needed (currently just `src/components/navbar.tsx`, for menu state and the
  theme toggle).
- Page-local content (subsidiary lists, testimonials, service bullets, stats)
  is defined as a typed array/object literal at the top of the page file, not
  fetched from anywhere. Keep following this pattern unless a feature
  introduces a real data source.

## Next.js

- App Router (`src/app/`), no `pages/` directory.
- Server Actions for form submissions (`"use server"` inline function, see
  `handleContactSubmit` in `src/app/contact/page.tsx`) - keep using this
  pattern for future mutations rather than adding API routes, unless a route
  is genuinely needed (webhook, file upload, etc.).
- Metadata via the declarative `Metadata` export in `layout.tsx` /
  `page.tsx`, including Open Graph fields.
- Dynamic/nested routes for subsidiary detail pages
  (`src/app/services/[sector]/page.tsx` pattern, one file per sector today).

## File Organization

- Pages: `src/app/[route]/page.tsx`.
- Shared components: `src/components/ComponentName.tsx` (flat, not yet
  split by feature - `navbar.tsx`, icon components).
- shadcn/ui primitives: `src/components/ui/ComponentName.tsx` (`button.tsx`,
  `card.tsx`), installed via the shadcn CLI (`components.json`), aliases
  `@/components`, `@/lib`, `@/hooks`.
- Utilities: `src/lib/utils.ts` (currently just the shadcn `cn()` helper).

## Naming

- Components: PascalCase (`Navbar`, `InstagramIcon`).
- Files: lowercase/kebab or matching component name (mixed today -
  `navbar.tsx` lowercase, `FacebookIcon.tsx` PascalCase; match whichever
  neighboring file you're closest to).
- Functions: camelCase.
- Types/Interfaces: PascalCase, no prefix.

## Styling

- Tailwind CSS v4, CSS-first config in `src/app/globals.css` via `@theme
  inline` and `:root` / `.dark` CSS variables (oklch colors) - there is no
  `tailwind.config.js`.
- shadcn/ui components (`style: radix-nova`, `baseColor: neutral`,
  `iconLibrary: lucide`) - extend by wrapping, don't rewrite the primitives
  in `src/components/ui/`.
- Dark mode via a `.dark` class on `<html>`, toggled client-side in
  `Navbar` and persisted to `localStorage` (not OS-preference-only). Light
  mode is the default; both are first-class.
- No inline styles except background-image URLs on hero sections
  (`style={{ backgroundImage: ... }}`), which is the established pattern for
  page banners - keep using it rather than inventing a different approach.
- Zinc-based neutral palette; gradient/overlay hero banners on interior pages.

## Data

- No database. If a future feature needs persistence (e.g. storing contact
  form submissions), that's a new architectural decision - propose it via
  `/feature`, don't default to Prisma or any specific ORM without discussing
  it first.
- No auth. Don't add Clerk/NextAuth conventions unless a feature explicitly
  requires user accounts.

## Error Handling

- The contact form's server action currently has no error handling and
  discards its input (`console.log` only, see `src/app/contact/page.tsx`).
  This is a known gap on the build plan (item 7), not a pattern to replicate
  elsewhere.
- When wiring real mutations, prefer a `{ success, data, error }` return
  shape from Server Actions and surface failures to the user in the UI
  (the existing success state, gated on `?success=true`, is the model to
  extend).

## Testing

No test runner is installed (`package.json` has no `test` script and no
Vitest/Jest dependency). Testing is opt-in, per the standard Blueprint rule:
adding a runner is a deliberate step, not a silent one.

- Run `/tests` when logic worth unit-testing appears (for example, once the
  contact form gets real validation/delivery logic).
- Until then, verify UI and page changes with the dev server, a screenshot,
  and `npm run build` - this project is almost entirely presentational, so
  most changes are UI/integration-level and exempt from a test gate.
- **The opt-in switch:** once a `test` command is added to the Commands
  section of `AGENTS.md`, tests become a gate for logic-bearing steps. Until
  then, there is none.

## Browser Verification

Playwright is not installed. Verify UI changes with the dev server
(`npm run dev`), browser screenshots, or the production build - don't add
Playwright silently mid-feature; only add it if the user asks or a spec is
explicitly about browser automation.

## Code Quality

- No commented-out code unless specified.
- No unused imports or variables.
- Keep functions under 50 lines when possible.

## Comments

Write code that explains itself; comment only what the code cannot say.
Over-commenting is a common AI tell, so resist it.

- Comment the **why**, not the **what**. Delete any comment that restates the
  code.
- No banner/header blocks, section dividers, or step-by-step narration of
  obvious code. A file does not need a comment announcing each region.

  > Note: the existing codebase does use `{/* Section Name */}` JSX comments
  > above major page sections (hero, grid, stats, etc.) as light navigation
  > aids in long files. Treat these as an established exception in this
  > project - keep the convention consistent within a file you're editing,
  > but don't add narration comments beyond that pattern.
- A comment earns its place only when it captures something the code can't: a
  non-obvious decision, a gotcha or workaround, why a value is what it is, or
  a link to a spec or issue.
- Prefer self-documenting names and small functions over explanatory
  comments.
- When in doubt, leave the comment out.

## Writing

- No em dashes (U+2014) in generated content: docs, comments, commit
  messages, READMEs, specs. They read as AI-generated.
- Use a hyphen for `term - description` separators; rephrase prose with
  commas, parentheses, or a colon. Avoid en dashes and the ellipsis character
  too.
